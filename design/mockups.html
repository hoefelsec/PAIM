Direction

Drafting table

This is an instrument, not a product — it lives in a folder on your machine and nobody else logs into it. So the palette borrows from drafting rather than from SaaS: a warm graphite ground the colour of pencil lead, and a desaturated blueprint blue as the only interaction accent.

The warmth is doing real work. Every project carries its own colour, which means the system accent has to stay quiet enough that a clay-red project and a sage-green project can sit side by side without the chrome shouting over either. Warm ground, cool accent, low-chroma semantics: the temperature contrast carries the hierarchy so saturation doesn't have to.

Type is the native macOS stack rather than Inter, with monospace reserved for things that genuinely are identifiers: task keys, field keys, status keys. If it's mono, you can put it in a URL.

Shell

One workspace at a time

A project is a workspace, not a sidebar item. Selecting one scopes the entire UI — every filter, every keyboard shortcut. You change it from the switcher in the top-left corner, the way you'd change workspace in Notion.

That frees the left rail for its real job: faceted filtering. Status, priority, type, difficulty, layer, labels — each a collapsible facet with live counts. And because type and difficulty are this project's custom fields while status and priority are core, the rail can't be hardcoded. It's generated from the same fieldSchema that drives the table columns: every select field becomes a facet automatically. Open a different workspace and the rail is different.

The split that follows is worth stating as a rule, because it settles a lot of small arguments later: the rail controls which tasks are in the set; the toolbar controls how that set is presented. Filtering lives left, view/sort/group live top. Nothing appears in both places.

Filters are ephemeral. They live in the URL, so a filtered view is shareable and the back button works, but they do not survive a workspace switch. A filter you forgot you set is indistinguishable from missing data. To keep one, press Save view — next to Sort and Group — which promotes the whole state (view, filters, sort, group, columns) to a stored record. When live state diverges from the selected view, the view name grows a dot and Save view turns accent.

AI

Write it badly, then run it

Claude is not an assistant panel bolted to the side. It is how tasks get written and how they get done — two integrations with genuinely different shapes.

Compose replaces the new-task form with a textbox. You describe the work however it comes out of your head; Claude maps it onto the workspace's schema and returns a draft. The mechanism is the nice part: the extraction schema is generated from the project's fieldSchema — the same source that validates API writes — so a workspace with difficulty gets difficulty extracted and one without it never sees the field. No per-project prompt engineering. Nothing is created until you press the button, and every inferred value is editable in place, because guessing wrong silently is worse than not guessing.

Run is the feature that changes what the product is. Everything else here is a task tracker; this makes it an execution surface. It's built on the Claude Agent SDK — Claude Code as a library — rather than a hand-rolled loop, because that package already ships the agent loop, the file and bash tools, and a permission callback that fires before every tool execution. Rebuilding those means rebuilding file editing, diffing, command execution and the approval gate, and getting all four right.

Which is where the design work actually is. A model that can write files and run commands needs a boundary, and "it's all local anyway" stops being a sufficient answer the moment it can run rm. So: every project carries an absolute workspace path, and one without it has no Run button at all. Operations are classified by what they can do — reads auto-run, writes and commands meet the project's policy — and the risk class is the visual axis on the run screen. The workspace path sits in the run header where you can't miss it.

Which model runs it is routed, not chosen. Every task carries a model and an effort, and both are normally inherited: you nominate one select field as the routing field and map its options — trivial → Haiku at low effort, hard → Opus at xhigh. Since difficulty is a custom field, routing couldn't be hardcoded to it without breaking the rule that holds everywhere else here: the schema drives the product, the product doesn't presume the schema. Either value can be pinned per task, and a pinned value looks different from an inherited one so you can tell at a glance.

Budget

Spending you can see, and stop

A band across the top of the main pane carries what the project is on the left — version read live from the workspace, task counts — and what it is costing on the right: the three usage windows your Claude credentials carry. The 5-hour rolling window, the weekly allowance, and the separate allowance for Fable, the most capable tier.

Each bar ends at the hard limit and carries a draggable marker: a cap you set for yourself, somewhere below it. The point isn't to visualise consumption — it's to reserve headroom deliberately. You decide this project may burn 70% of the window and no more, so whatever else you do today still has room. Runs are blocked at your marker, not at the hard limit, with the reason and the reset time stated rather than a greyed-out button.

Two details that follow from taking that seriously. The Fable cap gates by routing — in the mockup Fable is over its cap, so tasks routed to claude-fable-5 can't start while everything else runs normally, which is the whole reason the window is tracked separately. And a cap doesn't only block starting: it pauses a run already in flight, at the next operation boundary, and resumes it automatically when the window resets. Pausing isn't cancelling — completed operations stay applied, the agent keeps its context. In the dock, RCX-8 is sitting held for exactly that reason.

The bars are the whole notification. No banner, no toast. A meter that is visibly clay on every screen has already said it; a warning strip on top is the same fact twice, and the second copy is the one you learn to dismiss without reading.

There's a second limit that isn't about money at all. One run at a time, per project — because every agent writes to the same filesystem, and two of them in one workspace will interleave edits and clobber each other with neither noticing. That's a correctness constraint, not a throughput setting, and the settings copy says so. Different projects have different workspace roots, so they run alongside each other freely, which is why the dock legitimately shows three at once.

Control

Everything that's running, everywhere

The activity dock spans the full width of the window — under the sidebar, not inside the main pane. That placement is the whole argument: the dock is global, not workspace-scoped. A run you kicked off in Homelab an hour ago is precisely the thing you'd forget about while heads-down in Task Manager, so it sits in the one strip that never changes when you switch workspace. It's also the only screen besides the project grid where several project colours appear together, which is what that identity palette exists for.

Two honesty problems worth solving rather than papering over. Progress: once the agent has declared a plan the bar is real — completed operations over planned, 4/6. Before that there is no denominator that isn't invented, so the row shows an indeterminate shimmer labelled planning. A bar that makes up a percentage is worse than one that says it doesn't know yet. Cancel: cancelling doesn't roll back, so the confirmation's job isn't "are you sure" — it's naming the three files already changed and saying outright that they stay changed. Pause, meanwhile, stops at the next operation boundary and never mid-operation; a half-written file isn't a state worth being able to reach.

Safety is a floor and three modes. The floor is a two-entry deny list — rm -rf / and git push --force — which applies in every mode including Allow everything and is the one thing a task cannot override. Above it: allow everything · ask everything · ask for listed actions, set per project and overridable per task.

Deny and ask are different mechanisms rather than two strengths of one. The ask list is a tripwire — stop and show me — answered in the moment, run continues either way. The deny list is a refusal with no approve-anyway button; to run a denied command you edit the list in settings. That friction is the feature: it moves the decision out of a 1am approval prompt, where a mis-click costs a filesystem, and into a deliberate act with the pattern in front of you.

A denial doesn't kill the run, though — that would just make people disable the list to get work done. The refusal goes back to the model with its reason, so it adapts. The Run tab shows exactly that: a force-push refused, and the non-forced push it proposed instead, which then asks. Workspace confinement sits underneath all of it and is not a setting at all.

There is a way back, and it is narrower than "undo". Every run captures a restore point first — git-backed where it can be, file snapshots otherwise — and Restore rewinds the workspace while the task is unfinished, disappearing once it's done, because at that point the changes are the deliverable. What it can't reach is stated where it matters rather than in small print: the npm install row on the Run tab says so on its own line, and the cancel dialog now offers Cancel & restore against Cancel, keep changes and names the side effect neither can undo. A user who believes they've undone a push has not undone a push, and that is the one failure this feature must not have.

Approval is as you go, not plan-first — the agent works and each operation that needs you stops when it comes up, because a plan composed before the model has read any files is mostly guesswork. The dry-run toggle covers the case where you do want the plan: it runs normally, shows every operation and diff, and applies none of them. Default policy is ask everything; loosen it per project once you trust the shape of the work.

Epics

A task that happens to contain tasks

An epic is a task whose size is Epic. size runs XS · S · M · L · XL · Epic, and that last value is what makes the task one — kind is derived, never set. There is no way to have an XL epic or an Epic-sized task that isn't one. It's also why size is the single field that had to leave the custom schema and become core: a field that changes what kind of thing a record is can't be optional per project. Children point at it with parentId, and that is the entire model. Because it's a task it inherits statuses, priority, custom fields, filters, the table, model routing and runs — rather than needing a parallel implementation of each. A separate entity would have meant duplicating the schema engine, the view layer and the run pipeline for something that behaves almost identically.

It expands in place in the table: a disclosure triangle, 3/7 done, and children as indented rows sharing the same columns. Expanding is view state, not navigation, so you can open an epic, scan it against everything else, and collapse without losing your place.

Running an epic starts an orchestrator rather than a worker — one agent that reads the epic and dispatches the rest, one per subtask. It runs a tier above them, at max reasoning, because planning across seven subtasks is a harder problem than any one of them. Each subtask gets its own run record, its own operations and its own approvals, so a failure is attributable and the epic's other work is unaffected; the activity dock nests the children under the parent to keep that provenance visible. Concurrency is capped per project, because N parallel agents is N times the usage burn against the caps in the stats band.

Two things deliberately don't change. A child is an ordinary task — it appears in the table, matches filters, and keeps its own Run control, so being inside an epic constrains nothing. And safety is the stricter of epic and subtask: a permissive parent can't widen what its children are allowed to do. The one thing that is automatic: an epic moves itself to Done when the last child finishes, and back out if one reopens.

Lifecycle

Statuses the system acts on

Statuses are predefined, not per-project custom. They can't be custom, because the tool now does something at each one: it asks the questions, runs the tests, performs the review. A status the system has to implement behaviour for cannot be a string the user invents. So there's one predefined catalogue, and a project picks which stages apply. Order is fixed — you can skip testing, you can't put it before executing.

Four of them are gates, and each is a different answer to "why isn't this done yet". Open questions is Claude admitting it can't infer something rather than guessing and being confidently wrong. Design catches decisions that are cheap now and expensive once code exists — and Claude, not the button click, decides when the direction is unambiguous. Testing runs the project's regression suite plus whatever the task added. Review is Claude inspecting its own work by opening the app, then — if the project wants it — briefing you to inspect it yourself.

Every gate fails backwards to Executing, carrying its reason as the next run's brief: the failing test output, the review's objection. Forward movement requires clearing the gate, with no manual override, because a gate you can wave past is a gate nobody trusts.

Two things keep the pipeline from going stale. Dependencies are detected when the task is drafted and block running — you can still queue a blocked task, since forbidding that means babysitting the queue, but the queue stops it when its turn comes and names the unfinished dependency rather than starting work whose premise isn't true. And re-evaluation re-reads your original prompt against the project as it is now, reconsidering description, size, priority and dependencies — up to concluding the task isn't needed any more. It's suggested, never automatic: when a dependency lands, when questions get answered, when enough has changed underneath. The tool keeps sourcePrompt for exactly this, and silently rewriting what you wrote would be worse than letting it drift.

Density

Icons where the header already said it

Priority, type and difficulty render as glyphs with no text. The column header names the dimension, so spelling out Medium in every row costs width and buys nothing; the word appears on hover and in the filter rail, where you're choosing rather than scanning. Four text columns became four narrow ones and the titles got the space back.

The risk in that is two scales that look alike, so they use different languages: priority grows in bar height, difficulty fills in dot count. Difficulty's unfilled steps are rings rather than dim discs — at 5px a fill difference alone is unreadable, and ●○○○ versus ●●●● has to be legible at a glance or the column is decoration. Type isn't a scale at all, so it gets distinct silhouettes instead of a ramp.

Sort gains an AI option. Suggested orders tasks by how they influence each other, so work that reshapes a later task comes first and you don't build the same thing twice. It's a snapshot, not a live sort — edit the set and the chip marks itself stale rather than silently reordering under you — and every position carries a one-line because, since an ordering you can't interrogate is one you stop trusting the first time it looks wrong.

Screens

Seventeen screens, one shell

Real content throughout — these are this project's own tasks. Compose is a focused surface: it keeps the workspace switcher, because the workspace still scopes it, and drops the facet rail, because there's no task set to filter. Seven of these are the task view in different tab states — the tab row is the pipeline, so it doubles as a progress indicator.

The rail is generated

status and priority are core facets present in every workspace. type, difficulty and layer come from this project's schema — the small grey label on each facet head says which. Open Homelab and you get a different rail.

Filter left, present top

With filtering moved to the rail, the toolbar collapses to view, sort, group and count. No filter chips, no duplication — 16 of 28 is the only trace, and it's honest about what's hidden.

Epics expand in place

TM-20 is an epic — same table, same columns, a disclosure triangle and 3/7 done. Its children render indented beneath it rather than on another screen, so you can scan them against the same columns and collapse without losing your place.

Floating, because selection is transient

The bar appears over the table and above the dock, and leaves on Esc. Permanent chrome for a temporary state is chrome you look at all day for nothing.

"Run 3 separately" is not "make an epic"

Run queues three independent runs with no orchestrator and no shared plan. The label says separately so the difference is discovered before you press it rather than afterwards.

Merge is compose, pointed differently

Same pipeline as the AI composer — but the input is the selected tasks and the output is their parent. Claude drafts the epic's title, description and fields from the children, and like compose it returns a draft you edit before anything is reparented.

Ask rather than guess

Compose doesn't always have enough to work with. Rather than inventing an answer and being confidently wrong, the task lands here carrying what Claude actually needs to know — and there's no Run button, because there's nothing to run yet.

Answering re-evaluates

The answers change the task, so clearing the last one triggers a re-evaluation of description, size and priority before it moves to Ready. Answering a question and leaving a stale estimate behind would be half the job.

Choices or prose

Q2 offers options because there are only two sensible answers; Q1 didn't, so it took free text. Either way the reply is input to Claude, not a form field it writes down verbatim.

Decide before implementing

Where validation errors surface changes the API shape, so building first and deciding later means building twice. The design gate exists to catch exactly the decisions that are cheap now and expensive after the code exists.

Claude decides when it's resolved

Picking an option is input, not necessarily an answer. If your reply opens a new question the task stays in Design — the gate clears when the direction is unambiguous, not when a button was clicked.

Options carry their cost

Each card says what the approach gives up, not just what it does — "loses which field each warning belongs to", "costs a round trip". Three options with no trade-offs stated is a preference poll, not a design decision.

Regression plus task-specific

The project's suite runs on every task; a task can add its own on top. The Kind column keeps them distinguishable, because "did I break something" and "did I build the right thing" are different questions with different responses.

Failure is a loop, not a stop

A red test sends the task back to Executing with the output attached as the next run's brief — so the agent starts knowing what broke. It only moves forward when everything passes; there's no override, because a gate you can wave past is one nobody trusts.

The failure explains itself

The output isn't a stack trace dump — it names the expectation, the actual, and points at the answer from Q1 that the code contradicts. That's what makes it usable as a brief rather than just evidence.

AI review opens the app

It doesn't just read the diff — it spawns whatever views it needs to see the result, and says which ones. Here it caught a cache that survives project deletion, which no test covered and no diff makes obvious.

Manual review is briefed, not dumped

The one gate a model can't clear, so Claude's job is making yours small: what changed in plain language, a specific checklist of what to look for, and a way in. "Please review" with a diff attached is how review becomes rubber-stamping.

The checklist is falsifiable

Each item is an action with an expected result — write Homelab's key to a Task Manager task, it should be rejected. Not "check validation works", which you can convince yourself of without looking.

An epic is a task

It carries kind: "epic" and nothing else is special — so it inherits statuses, priority, custom fields, filters, routing and runs instead of needing a parallel implementation of each. Children point at it with parentId.

Run epic spawns an orchestrator

One agent reads the epic and dispatches the rest, one per subtask, each with its own run record and approvals. It runs a tier above the workers — max reasoning here — because planning across seven subtasks is harder than any one of them.

The epic never captures a task

Every child keeps its own ▶ control. TM-12 is mid-run on its own right now while the rest sit idle — being inside an epic constrains nothing.

The schema writes the prompt

Claude extracts type, difficulty and layer because they're in this workspace's fieldSchema — the same source that validates API writes. A workspace without them never sees them. No per-project prompting.

Draft, not commit

Nothing is created until you press the button. Every inferred value is editable in place, and the model's confidence shows as absence: assignee is left empty rather than guessed, and says so.

Show the cost

Model, latency and token counts sit in the footer of every AI surface. A tool that spends your money on each keystroke should say how much, where you can see it without going looking.

Risk is the visual axis

Operations are coloured by what they can do, not by what they are: read/grep neutral, write/edit steel, bash clay. Reads auto-run; writes and commands meet the workspace's approval policy.

Refused, then adapted

git push --force hit the deny list — struck through, refused, no approve button. The refusal went back to the model with its reason rather than killing the run, so it proposed a plain push instead, which lands on the ask list. Two mechanisms, one sequence.

Restore, and its honest edge

Rewinds the workspace to before the run — files reverted, created files removed — and disappears once the task is done. It can't undo the npm install, and that operation says so on its own row rather than in small print. A user who believes they've undone a push has not undone a push.

A different question from the run log

The Run tab answers what happened, in order — per-operation diffs of one run. Code review answers what does the tree look like now: the cumulative diff across all three runs this task took, which is what you'd actually review.

Three sub-tabs, three jobs

AI review is a verdict with a reason. Code review is the evidence. Manual review is the brief. Collapsing them into one scroll would bury the verdict under 128 lines of diff.

The comment earns its place

evictProject carries a note explaining why deletion must evict — the recreated-slug case the AI review caught. That's the constraint the code can't show, which is the only kind of comment worth keeping.

Global, not workspace-scoped

The dock spans the full window — under the sidebar, not inside the main pane — because it shows every run in every project. That's the point: a run you started in Homelab an hour ago is exactly what you'd forget while working here.

Progress that admits ignorance

Once the agent declares a plan the bar is real: 4/6 operations. Before that there's no honest denominator, so RCX-8 shows an indeterminate shimmer labelled planning rather than a fabricated percentage.

The dialog's job is one sentence

Cancelling does not roll back. So the confirmation names the three files already changed and says so outright, rather than asking "are you sure?" and letting you assume an undo that doesn't exist.

The folder is the wiki

This is docs/ inside the workspace, rendered — not an import. Edit the files in your editor, commit them with the code, and the tool shows whatever is on disk now. No docs/ folder means the button is disabled and says why.

The rail is contextual

Same slot, different content: facets on a task list, the file tree here. Filtering has nothing to act on in a document, the same reason the rail is absent from compose and run.

Rendered to the design system

Markdown picks up the type scale, mono treatment and code-block styling from the tokens below, so a doc reads like part of the tool rather than a browser default. Images render inline; relative links navigate in-app.

Scope, not navigation

Picking a workspace here re-scopes the whole UI, so it earns a dedicated menu rather than a list you scroll past all day. Open counts sit inline so the choice is informed.

Where the exits live

Project settings, New project and All projects hang off the bottom of this menu. They're workspace-level actions, so they belong where the workspace is chosen — not in a separate settings hunt.

Archived stays reachable

One collapsed row rather than a hidden preference. Archived projects can still be opened as workspaces, and stay fully addressable over the API regardless.

Panel, not a page

The detail slides over the list so surrounding rows stay visible and you never lose your place in a triage pass. Still deep-linkable — /t/TM-3 loads full-page on a cold open.

Edit in place, always

Size is mid-edit here. Click a value, pick, blur to save. No modals, no Save button, and the write goes out optimistically — the row behind updates before the server answers. Setting it to Epic is what promotes a task.

No author, only time

Writes are anonymous, so the panel ends in timestamps rather than an activity feed. assignee survives because it's a value you set, not one derived from who made the request.

No rail here

Root is pre-workspace: nothing is scoped yet, so there's nothing to filter. The grid gets the full width, and picking a card enters that workspace.

Colour as identity

Each project's colour appears as a tinted icon tile and its progress meter — never as a rail down the card edge. Tinted fill keeps five hues on screen without any of them dominating.

Open count leads

The number you act on is bold and first; completed work is secondary. The meter reads as done-over-total without needing a percentage label.

The rail, a third time

Facets on a task list, a file tree in docs, a section nav here. Same slot, contextual content — the rail always answers "what can I navigate within this surface", and settings has enough sections to need it.

A floor, then three modes

The deny list sits above the radio options because it isn't one of them — it applies in every mode, including Allow everything, and no task can override it. The ask list below asks and never refuses, which its own copy says outright since "blacklist" would imply the opposite.

Auto-push is not auto-commit

Committing is local and reversible, so it's a plain toggle. Pushing publishes model-authored commits where teammates and CI see them, so it gets the clay treatment, an explanation of consequence rather than a restated label, and a dependency on auto-commit.

Two toggles, two surfaces

Column puts a field in the table; Facet puts it in the left rail. layer is a facet but not a column; effort is both; spike is neither.

Removal is soft

spike is hidden but still holds values on four tasks, and says so. Nothing about "remove this field" should feel like it might be destructive, because it isn't.

Keys are mono, labels are not

difficulty in blue mono is the identifier an agent writes; "Difficulty" is what you read. The typographic split is the whole convention — mono means addressable.

Geometry

  • 4px spacing grid. Table rows 33px, facet items 25px, rail 240px, detail panel 430px.
  • Radii by role: 6px controls, 10px cards, 14px panels. Never larger — soft corners at this density read as toy-like.
  • 1px hairlines, not shadows. Structure comes from borders and background steps. The only elevation shadows are the workspace menu and a card mid-drag.
  • Tabular numerals anywhere digits stack: facet counts, effort, timestamps.

Motion & interaction

  • 120–200ms, ease-out. Menu open, panel slide, facet collapse, view switch. Nothing longer, nothing decorative.
  • Hover is instant (0ms in, 140ms out) so scanning a table never feels laggy.
  • Optimistic first. The UI commits immediately and reconciles on response; a rejected write flashes the row clay and reverts.
  • Keyboard: ⌘K palette · ⌘P switch workspace · C new · / search · J/K move · E edit · Esc close.
  • prefers-reduced-motion drops every transition to zero.

Open questions

Nothing outstanding

Every decision is made. The specification lives in docs/, split into fifteen documents with a glossary and a banned-terms table, written in ASD-STE100 Simplified Technical English.

Four values are answers rather than conclusions: staleness after 14 days, staleness after 10 completed tasks, 30-day trash retention, and one concurrent agent per project. They are first estimates. docs/15-open-questions.md lists them so a measurement can replace them.

The last decision removed a setting rather than adding one. Two numbers described one constraint — the count of agents writing to a single workspace — and a configuration that satisfied both could still corrupt files. maxConcurrentRuns now counts every agent in a project, including an epic's subtask agents.
